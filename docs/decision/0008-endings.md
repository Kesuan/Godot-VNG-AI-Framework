# 0008 · 结局标记与结局页面

- 状态：已接受
- 日期：2026-10-14
- 关联决策：[0002](0002-story-dsl.md)、[0006](0006-multi-chapter-and-save.md)、[0007](0007-ux-layer.md)

## 背景

多章剧本完成后需要区分"达成了哪个结局"，并在结束后给玩家明确的收束页面（而不是直接淡出回标题）。`-> END` / `-> STORY_END` 只表达"在哪结束"，不表达"是什么结局"。

## 决策

### 1. 结局标记 `@ending <id>`

- 节点内指令，通常置于 `-> END` / `-> STORY_END` 之前；
- 编译为 `{op: "ending", id}` 步骤；运行时记录 `ending_id` 并发出 `ending_reached` 语义事件；
- 一个剧本可登记多个结局；同一路线多次执行 `@ending` 时以最后一次为准（当前无此用法）。

### 2. 结局登记（`story.json` 的 `endings`）

- `endings`：结局 id → `{title, subtitle}` 映射；
- linter：引用未登记的 id → 错误（带 did-you-mean）；登记但无任何引用 → 警告；
- 标题/副标题用于结局页面展示。

### 3. 存档与 trace

- `ending_id` 进入运行时快照与存档（v2 新增可选字段，旧档兼容：缺省为空）；
- trace 归约包含 `ending_reached {id}`；新增 golden 含该事件，既有 golden 不受影响。

### 4. 结局页面

- 剧情结束后：`session.ending()` 非空 → 展示结局页面（「结局」标签 / 标题 / 副标题 / 回到标题）；为空 → 直接回标题（兼容无结局剧本）；
- 结局页只负责展示与返回，不写存档（自动档在进入章节时已写入）。

## 后果

- 多结局与隐藏结局用同一套机制表达（配合条件链与 flag）；
- 结局 id 成为后续"结局收集 / 成就 / 结局页回顾"的天然主键。

## 被否决方案

| 方案 | 否决原因 |
| --- | --- |
| 用最终节点 id 隐式表示结局 | 节点重构即漂移；`@ending` 显式且可 lint |
| 把结局写进 `-> END <id>` 语法 | 终结语义与元数据耦合，解析与 lint 复杂化 |
| 结局页面写存档 | 存档职责单一（剧情屏写入）；页面只展示 |
